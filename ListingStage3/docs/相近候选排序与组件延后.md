# 相似候选按采集排名排序，组件匹配延后

## 当前执行顺序

硬条件筛选 → 产品卖点与视觉风格综合评分 → 按综合分取前N套 → 相近分数组内按采集排名升序 → 输出整体候选。

保持整体优先，不按销量直接加分。ranking使用第二阶段overall_features.historical_rank，此值是历史采集记录，不代表实时BSR；没有可靠BSR依据时也不能把该字段解释为销量排名。国家、站点和品类不同的同组候选不比较历史排名。未来不同排名入口、类目、观察批次混合前，需要增加排名证据范围标识，不能直接比较这些数值。

## 配置

config/runtime.json的retrieval字段：

```json
{
  "whole_top_k": 3,
  "rank_tiebreak_tolerance": 0.02,
  "match_components": false
}
```

whole_top_k可改成5、10等任意正整数，不写死3。先按语义综合分选定N套，排名不会把范围外的低相似候选挤进来。

rank_tiebreak_tolerance默认0.02，采用绝对分差，不是2%的置信度。候选先按综合分降序，每组以最高分为锚点，组内最大分差不超过该值，再按有效采集排名升序排序；未知排名放在组内有效排名之后。不采用相邻差链式分组，避免跨越大分差。设为0时保持严格综合分排序。该值是初始配置，需业务样本校准。

例如0.637200（采集1）、0.627661（采集41）、0.622390（采集5）在同一接近组，输出顺序为1、5、41。所有分数保持原值，展示顺序不再保证全局分数递减。结果包含proximity_group、group_anchor_score和capture_rank_tiebreak_applied供核对。

## 组件为何延后

原实现是为了检查候选整体内能找到哪些用途图文，提前执行组件相似度排序，只提供参考预览，不生成素材。现在默认match_components=false，reference_needs可省略或为空；即使输入了用途，本轮也只保留输入、不执行组件用途检索。

返回component_matching.status=deferred_to_generation_planning，reference_needs=[]。整套来源记录仍可追溯，原有组件向量、开关及文件没有删除。preview_image只是原Listing主图预览，不代表选择了生成参考。若填写style，风格评分仍会读取图片描述向量；这属于整体排序的证据，不属于生成组件挑选。

后续生成规划明确每张图片和每段文案用途后，可将match_components设为true，再执行候选内组件检索。当前开关只是复用已有能力，不是完整的生成阶段；将来应传入运营确认的整体版本ID，固定参考范围，再完成具体组件挑选。

## 实测

outputs/soft-lightweight-whole-only-20261103/index.html：纯中文柔软、轻便，无风格和结构限制，50套库，整体顺序1、5、41，组件匹配暂缓。原纯中文短句检索的不足仍然存在，此排序变更不等于改善了中文向量的语义理解能力。
